다음 요청을 역할 체인 워크플로우로 진행한다.

요청: $ARGUMENTS

## 1. 등급 판단 (먼저 사용자에게 명시)

| 작업 유형 | 적용 |
|---|---|
| 단순 문서/한 줄 수정 | 메인 세션이 바로 처리, 간소화 보고 |
| 구조 변경 없는 작은 코드 수정 | PM 간단 범위 → PL 작업 경계 → 승인 → PA |
| 여러 파일/모듈 | PM → (필요시 CTO) → PL → 승인 → PA |
| 아키텍처/보안 영향 | PM → CTO 상세 검토 → PL 분리 → 승인 → PA |

"요청이 구체적이다", "파일 하나다", "기존 코드를 재사용하니 리스크가 낮다"는 이유로 등급을 낮추지 않는다.

## 2. 승인 전 단계 ("단순 문서/한 줄 수정"이 아닐 때)

1. 요청과 직접 관련된 파일만 read-only로 탐색한다. repository 전체를 반복 스캔하지 않는다.
2. `Agent(subagent_type: "pm")`으로 목표/범위/비범위/산출물/승인 지점/완료 기준을 받는다.
3. `Agent(subagent_type: "cto")`로 기술 리스크·대안을 받는다. 리스크가 낮아도 "리스크 낮음 — 이유"를 CTO 산출물로 받는다. 메인 세션이 PM/CTO 판단을 지어내지 않는다.
4. **`EnterPlanMode`를 실제로 호출**한다. 채팅에 "승인 전까지 수정하지 않겠다"고 적는 것은 게이트가 아니다.
5. plan을 역할별 섹션으로 작성한다.
   - `## PM 요약`: 목표/범위/비범위/산출물
   - `## CTO 검토`: 리스크, 대안, 사용자 승인 필요 항목
   - `## PL 작업 경계`: 건드리는 파일/레이어, 재사용할 기존 코드, 작업 순서, PA 분리 여부
   - 필요 시 `## 구현 범위`, `## 검증`
6. `ExitPlanMode`로 승인을 요청한다. 응답을 승인 / 거부 / 보류 / 재요청 중 하나로 해석한다. 거부·재요청이면 반려된 단계의 역할이 다시 제안한다.

승인이 필요한 항목: 범위·기술 방향·아키텍처 확정, 신규 의존성, 보안/인증/권한/배포 변경, 리스크·기술 부채 수용, 계획에 없던 새 파일, 범위 밖 파일 수정, 병렬 PA 실행.

## 3. 승인 후 실행

1. `Agent(subagent_type: "pl")`에 승인된 plan 전체를 전달한다.
2. PL이 PA 작업 카드를 만들어 `pa` subagent를 실행하고, PA는 완료 전 `reviewer`를 동기 호출해 PASS 최종본만 PL에 넘긴다.
3. 중첩 Agent 호출이 막혀 PL/PA가 BLOCKED를 보고하면, 메인 세션이 reviewer 호출과 PA 재작업을 직접 중계한다. 검토 완료를 주장하지 않는다.
4. 실행 중 승인 범위를 벗어나는 문제가 생기면 기존 승인을 확대 해석하지 않고 다시 승인을 요청한다.

## 4. 사용자 보고

PA 종료 시 Stop 훅이 콜백 보고를 강제한다. 최종 보고는 다음 형식을 따른다.

```md
## 완료 보고
- 완료한 작업:
- 변경된 파일:
- 검증 방법과 결과:
- Reviewer 기준·범위·최종 판정:
- 지적사항별 추천 → PA 수정 → 재검증:
- PL 수용/보류 결정과 이유:
- Prompter 추천 및 승인 상태 (있는 경우):
- 에러/불가 처리:
- 남은 이슈:
```

단순 작업은 간소화한다.

```md
## 간소화 보고
- PM: (생략 이유)
- CTO: (생략 이유)
- PL: (생략 이유)
- PA: 처리 결과
```

실패·보류·미검증 항목을 숨기지 않는다. 기록이 필요한 에러/크리티컬/개선사항은 `/review-log`로 제안한다.
