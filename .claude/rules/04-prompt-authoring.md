# 프롬프트 작성 규칙

## agent (`.claude/agents/<name>.md`)

```md
---
name: <kebab-case 역할명>
description: <무엇을 하는 역할인지 + 언제 호출하는지>
tools: <필요한 최소 도구>
---

<역할 정의 한 문단: 누구이며 무엇에 가치를 두는가, 응답 언어>

## 책임
## 산출물 형식   (다음 역할이 바로 쓸 수 있는 md 템플릿)
## 금지
```

- `description`은 호출 조건이 드러나게 쓴다. 메인 세션이 이 문장으로 agent를 고른다.
- `tools`는 최소 권한으로 둔다. 검토·추천 역할(reviewer, prompter)은 `Read, Glob, Grep`만 준다. 하위 agent 호출이 필요하면 `Agent(name, ...)`로 대상을 제한한다.
- agent 본문의 `@경로`는 자동 import되지 않는다. 필요한 문서는 "Read로 확인한다"고 명시한다.
- 산출물 형식은 고정 필드로 쓴다. 훅이 검사하는 필드(`REVIEWER_STATUS` 등)는 바꿀 때 훅도 함께 바꾼다.
- 역할 경계(하지 않는 것)를 반드시 `금지`에 적는다.

## command (`.claude/commands/<name>.md`)

- frontmatter에 `description`, 인자가 있으면 `argument-hint`를 둔다.
- 본문에서 `$ARGUMENTS`로 요청을 받는다.
- 절차는 번호 목록으로, 보고 형식은 md 템플릿으로 쓴다.

## rule (`.claude/rules/NN-<topic>.md`)

- 매 세션 자동 로드되므로 짧고 단정적으로 쓴다. 이유는 위반 사례 등 꼭 필요한 만큼만 남긴다.
- `03-md-authoring.md`의 frontmatter·번호 규칙을 따른다.
- 같은 규칙을 여러 파일에 중복 정의하지 않고 한 곳을 가리킨다.

## 작성 원칙

- 문장은 "~한다 / ~하지 않는다"처럼 행동 단위로 쓴다.
- 금지는 근거가 된 실제 실패 패턴이 있으면 함께 적는다.
- 프로젝트 고유 맥락(`docs/` 요구사항, 스택)을 반영하고, 쓰지 않는 기술 스택 규칙은 넣지 않는다.
- 새 전문 agent(security, DBA 등)는 그 관점이 반복적으로 필요함이 확인된 뒤에만 만든다.

## 프롬프트·MD 변경 승인

1. 반복 지시, 규칙 충돌, 누락을 발견하면 `prompter`에게 추천을 받는다.
2. 대상 파일과 변경 전/후를 사용자에게 제시한다.
3. 사용자가 명시적으로 승인한 범위만 메인 세션 또는 PA가 반영한다. prompter는 승인 후에도 직접 수정하지 않는다.
4. 사용자의 침묵, 다른 역할의 동의, 작업 전체에 대한 포괄적 동의는 개별 변경 승인이 아니다.
5. 반영 범위가 바뀌면 다시 승인을 받는다. 승인된 추천과 대기 중인 추천을 구분해 보고한다.
