# 작업 시작 전 워크플로우 게이트 (필수)

사용자는 최종 승인자다. AI는 의견, 계획, 검토, 실행 결과를 제공하지만 스스로 승인할 수 없다. 상세 실행 절차는 `/workflow` 커맨드를 따른다.

## 작업 등급

작업을 시작하기 전에 등급을 판단하고 사용자에게 명시한다.

| 작업 유형 | 적용 |
|---|---|
| 단순 문서/한 줄 수정 | 메인 세션이 바로 처리, 간소화 보고 |
| 구조 변경 없는 작은 코드 수정 | PM 간단 범위 → PL 작업 경계 → 승인 → PA |
| 여러 파일/모듈 | PM → (필요시 CTO) → PL → 승인 → PA |
| 아키텍처/보안 영향 | PM → CTO 상세 검토 → PL 분리 → 승인 → PA |

"요청이 구체적이다", "파일 하나뿐이다", "기존 코드를 재사용하니 리스크가 낮다"는 이유로 등급을 낮추거나 게이트를 생략하지 않는다. 요청의 구체성·작업 크기와 승인 절차는 별개다.

## 게이트는 도구로 강제한다

- "단순 문서/한 줄 수정"이 아니면 read-only 탐색 후 다음 도구 호출은 `EnterPlanMode`여야 한다.
- 채팅에 "승인 전까지 수정하지 않겠다"고 적는 것은 게이트가 아니다. 아무것도 차단하지 못한다.
- PM/CTO 판단은 메인 세션이 지어내지 않고 `pm`/`cto` subagent 산출물로 받는다.
- 승인은 `ExitPlanMode`로 받고, 승인 후에만 `pl` subagent → `pa` subagent 순으로 실행한다.

### 반복된 위반 패턴

1. 요청이 구체적이라는 이유로 PM/CTO 단계 없이 여러 계층을 바로 구현함.
2. "범위부터 정리하겠다"고 적고 `EnterPlanMode` 없이 같은 턴에 Edit함.
3. "단일 파일, 낮은 리스크"라고 스스로 판단하고 승인 없이 실행함.

공통점은 판단 후 다음 행동이 **말**이었고 `EnterPlanMode` **호출**이 아니었다는 것이다.

## 승인 대상

- 작업 범위·기술 방향·아키텍처 확정
- 신규 의존성 추가, 보안/인증/권한/배포 방식 변경
- 알려진 리스크·기술 부채 수용
- 병렬 PA 실행
- 계획에 없던 새 파일 추가, 범위 밖 파일 읽기·수정
- 실제 구현 시작, 최종 산출물

## 승인 상태

승인 / 거부 / 보류 / 재요청 중 하나로 판단한다. 거부·재요청이면 반려된 단계의 역할(PM/CTO/PL)이 새 안을 다시 제안하고, PA는 새 지시 없이 재진행하지 않는다. 승인 후 범위를 벗어나는 문제가 생기면 기존 승인을 확대 해석하지 않고 다시 승인을 요청한다.

## 자동 진행 금지

- 한 역할 산출물 직후 사용자 확인 없이 다음 역할 산출물을 이어서 작성하지 않는다.
- 에스컬레이션 요청과 그 응답을 사용자 확인 없이 연속 작성하지 않는다.
- AI 검토 결과를 사용자 승인으로 대체하지 않는다.

## plan 문서 형식

역할별 판단을 구분해서 읽을 수 있도록 섹션을 나눈다.

```md
## PM 요약
- 목표 / 범위 / 비범위 / 산출물

## CTO 검토
- 기술 리스크 / 함정·제약 / 검토한 대안   (리스크 낮아도 "리스크 낮음 — 이유"로 남긴다)

## PL 작업 경계
- 건드리는 파일·레이어 / 재사용할 기존 패턴 / 작업 순서 / PA 분리 여부

## 구현 범위   (필요 시)
## 검증         (필요 시)
```

승인 요청 전 확인: 목표·범위·비범위, 리스크·대안, 작업 경계·검증 기준, 사용자가 선택할 결정지, 승인하지 않을 때의 대안.
